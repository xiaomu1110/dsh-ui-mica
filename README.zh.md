# dsh-ui-mica

为 DeepSeek Harness 的**侧边栏**与**顶部栏**提供云母（Mica）材质背景，并在
**设置 → 通用** 里提供一个开关按钮。

![浅色主题下的侧边栏与顶部栏云母材质](docs/preview-desktop-light.png)

![深色主题下的同一材质](docs/preview-desktop-dark.png)

## 它做了什么

侧边栏列与 Windows 顶部栏行本是同一个表面的两个切片，插件就把它们当成一个表面来
画，叠放顺序与 DWM 合成云母时一致：**底色是当前桌面壁纸的重度模糊降采样**——宿主
半在 Node 里把壁纸读一次，用 `sharp` 缩到 192×108 再模糊，编码成约 1.4 kB 的
data URI 内联进样式表——上面盖一层宿主表面色，再叠高光与细颗粒。表面色由
`--dsw-alias-bg-base` 推导，于是同一张壁纸在浅色下是淡彩、深色下是暗彩，跟随主题
自动变化。

读不到壁纸时（非 Windows、profile 里没有 `sharp`、文件不存在或解不开）会回退到一
片就地绘制的色调场：面板仍然成立，只是颜色不再来自取样。样式表开头会写明这一次用
的是哪一种，在开发者工具里一眼可辨。

只有这两个表面。中间栏、应用框架、`html`、`body` 与 `#root` 一律保持宿主原本的
样子。

## 安装

```sh
dsh plugin --profile <profile> add dsh-ui-mica
```

安装后需要重启 Harness。运行中的 `dsh web` 只在启动时组合 bundles，所以插件要
等下次启动才会被加载。

## 设置

**设置 → 通用 → 云母背景**用于开关材质。开关即时生效：两个方向都不需要刷新，
也不会闪烁。

另外几个外观参数没有出现在界面里。在 profile 的 `cordis.patch.yml` 中设置，然后
刷新页面：

```yaml
- insert:
    - id: ui-mica
      name: dsh-ui-mica
      config:
        enabled: true       # 与设置界面里的开关是同一个值
        opacity: 62         # 20–92：面板里保留宿主表面色的百分比
        wallpaper: true     # 从桌面壁纸取色；关掉就用下面的绘制场
        wallpaperPath: ""   # 覆盖壁纸文件位置，留空表示自动探测
        tint: 100           # 0–200：回退色调场的强度百分比
        noise: 0.06         # 0–0.3：颗粒层的透明度
```

`opacity` 是「面板里有多少是宿主表面色」，所以 62 意味着大约 38% 的壁纸透出来。
如果觉得面板上的文字对比度不够就调高它，想让壁纸更明显就调低它。`tint` 只在回退
路径上有效，`wallpaperPath` 则用来指到别的图片——macOS、Linux，或者只是想换一张
壁纸试试。

## 实现方式

插件分两半，而 CSS 只有一半拥有。

**`lib/index.js` —— 宿主半。** 它声明六个 `volatile()` 配置字段，关掉 schema
自动生成的设置页（浏览器半自己画那一行），并挂上 `webserver/index-inject`，向每
次渲染的 `index.html` 推入两项内容：

- 一个 `<style>`，装着全部材质样式；
- 一个 `<script>`，在首帧之前就把 `data-dsh-mica` 写到 `<html>` 上。

第二项正是「不会闪一下未样式化的界面」的原因：浏览器半加载得远晚于首帧，晚到的
属性会表现为肉眼可见的跳动。

**`lib/client.js` —— 浏览器半。** 它通过 `configForms` 读取 `ui-mica` 设置命名
空间，把 `enabled` 映射到文档根元素上，并注册设置界面里的一行。它自己不带任何
CSS。

**所有选择器都被 `html[data-dsh-mica="on"]` 门控。** 这是整个设计的承重属性：
开关只是一次属性翻转，样式表每页只注入一次，关闭状态也不可能留下「卸了一半」的
材质。

还有六个值得一提的取舍：

- 壁纸是在**宿主半取样**的，而且刻意不在渲染路径上。`webserver/index-inject` 是
  同步的，等不了一次图像解码；所以第一次 index 渲染拿到的是回退场，样本稍后落地，
  下一次页面加载才用上壁纸。重新取样由文件的 `mtime` 与大小驱动而不是定时器，壁纸
  没变时每次渲染只多一次 `stat`。采样参数由实测选定：192×108、lanczos3 降采样、
  模糊 6、WebP q80，出图 1028 字节——放大 6.5 倍后没有 JPEG 块状伪影。之所以先降
  采样再模糊而不是反过来：源图是 1920×1200 的 JPEG，缩小本身就能把 8×8 的压缩块
  平均掉。
- 面板填充色是**推导**出来的，而不是写死的：
  `color-mix(in srgb, var(--dsw-alias-bg-base) <opacity>%, transparent)`。
  因此它会跟随当前主题——浅色、深色，或任何第三方主题——不需要维护一张按配色分
  支的对照表。
- 侧边栏内层的 root 会把 `--dsw-specific-sidebar-fill` **再画一遍**，压在列之上，
  而那个填充色是不透明的。插件在列上清掉这个 token，让侧边栏塌回单层绘制；顶部栏
  没有这样的子元素，不做这一步两块面板就会明显不一致。之所以清 token 而不是去
  「中和」读取它的元素：内层 root 是列的外孙而非子元素，子选择器够不到它；而
  `[class*="_root"]` 又会命中侧边栏里一堆无关元素。继承不需要选择器，也不会搞错
  层级。
- 色调场用 `background-attachment: fixed`。顶部栏与侧边栏列的高度分别是 36px 和
  ~700px，百分比尺寸的渐变在两者中会解析成完全不同的形状，接缝处两块面板因此明
  显不一致。把两个盒子锚定到同一片视口大小的场之后，接缝消失，颗粒相位也保持
  一致。
- 材质靠 `!important` 胜过主题呈现器。呈现器把 token 写成 `<body>` 上的行内自
  定义属性，而这恰好是样式表能够覆盖的形态；这里没有任何地方依赖宿主「愿意」降
  低自己的特异性。
- 两块面板**没有边缘线**。Windows 桌面端本来就给侧边栏列设了 `border-right:
  none`，顶部栏也从没有边框，所以那两块表面上唯二的线是 0.2.0 自己画的发丝线，
  0.2.1 已删掉。纯浏览器标签页里宿主确实会画一条 `.5px` 的边框，插件把它的**颜色**
  清成透明而不是删掉边框：保留那半个像素的盒子，关掉材质时就不会有位移。

## 刻意不做的事

下面两件事在 0.1.0 里是缺陷，现在都由 `scripts/smoke.mjs` 里的断言钉住。

- **任何地方都不用 `backdrop-filter`、`filter`、`transform`、`contain`、
  `will-change`、`perspective`。** 这些属性会让元素成为 `position: fixed` 后代
  的包含块。侧边栏开关是整个外壳里唯一的 fixed 元素，于是把 `backdrop-filter`
  加在侧边栏列上，就把它从顶部栏里拽了下来、压在鲸鱼 LOGO 上。云母本来也不模糊
  面板背后的内容，所以省掉这些没有任何损失。
- **没有任何规则重绘 `html`、`body`、`#root`、应用框架或中间栏。** 0.1.0 把
  `body` 改透明又画了一片铺满视口的底景，结果把对话区也染了色。半透明的面板是装
  饰，半透明的正文墙是缺陷。

## 已知限制

- **纯浏览器文档里没有顶部栏。** Harness 只在 Windows 桌面端设置
  `data-windows-titlebar`；浏览器标签页里没有可绘制的顶部栏，因此那里只有侧边栏
  会变化。这是宿主的版式，不是插件的缺失。
- **界面之外的参数需要刷新页面。** 它们在 index 被送出时读取，所以在 YAML 里改动
  影响的是下一次页面加载，而不是当前这一次。
- **材质假定宿主保留它的 `--dsw-*` token。** 它是在主题之上叠加，而不是替换主
  题；如果宿主改名了这些 token，面板会变得没有背景，而不会把界面弄坏。
- **这是云母的仿真，不是云母本身。** 颜色现在确实来自你的壁纸，但合成仍然发生在
  渲染进程里；真正的 Windows Mica 由 DWM 合成，只有 Electron 主进程的
  `new BrowserWindow({ backgroundMaterial: "mica" })` 才能开启，渲染进程里的插件
  够不到。宿主自己知道这条路——它的欢迎窗口在 win32 上用的是
  `backgroundMaterial: "acrylic"`，而主窗口只用 `titleBarOverlay` 铺了一个不透明
  的底色。所以「不够像」的一部分是应用层的选择，不是插件的。
- **壁纸来源只有 Windows。** 读的是 Windows 摊平后的那份文件
  `%APPDATA%\Microsoft\Windows\Themes\TranscodedWallpaper`；macOS 把壁纸记在二进制
  plist 里，本插件不去解析。其它平台用 `wallpaperPath` 手动指定即可。
- **需要 profile 里已经有 `sharp`。** 插件不把它声明成依赖——为了一张一 KB 的缩
  略图往 profile 里塞一个原生模块太重了——只声明为 optional peer 并在运行时解析。
  Harness 自带它，所以通常不必操心；没有时静默回退到绘制场。

## 开发

没有构建步骤。两半都以手写 JavaScript 形式发布，因此下面这些脚本就是 TSX 插件
的「编译并检查」阶段。

```sh
node scripts/check.mjs   # 静态 bundle 不变量（那个不存在的「构建」）
node scripts/smoke.mjs   # 用桩宿主真正运行两半代码
```

`smoke.mjs` 断言的是行为以及上面那些 CSS 不变量。这两个脚本都无法告诉你材质**看
起来**如何，而这个边界值得说清楚：0.1.0 是两套测试全绿、屏幕上却是错的，因为测试
模拟宿主，而它们并不是宿主。任何关于渲染结果的事情——面板颜色、两块表面的接缝、
控件有没有移位——都必须在一个真实的 Harness 实例上验证，从运行中的页面里读计算
样式。具体来说：

- 顶部栏与侧边栏在相接处必须量到相同的颜色；
- 侧边栏开关在材质开启时必须和关闭时坐标一致；
- 对文档中每个元素做一次开/关差异比对，结果里只能出现侧边栏。
